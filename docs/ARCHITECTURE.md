# Architecture

## Goals

- Strongest practical coding agent without a single subscription.
- Users bring their own API keys. Free tiers first, paid when the task deserves it.
- Every token accounted for. Spend is visible, never a surprise.
- Self-hosted, single user in v1. Data model leaves room for multi-user later.
- No local models.

## Why OpenCode as the engine

- Most-starred open-source coding agent (~200k), MIT, active.
- Built as client/server. `opencode serve` exposes an OpenAPI 3.1 spec, a TS SDK (`@opencode-ai/sdk`) and SSE events. Custom front ends are a supported use.
- Provider-agnostic through the Vercel AI SDK. Model catalog from models.dev with per-token prices, context limits and modality flags.
- Already tracks `cost` and `tokens` (input, output, reasoning, cache read/write) on every assistant message and rolled up per session. The ledger reads this, it does not estimate.
- Native Agent Skills (`SKILL.md`), MCP, Plan/Build agents, subagents, LSP diagnostics, auto-compaction.

The engine sits behind one interface (`src/server/engine`). If OpenCode ever becomes a blocker, OpenHands SDK is the fallback.

## What syrup adds on top

| Concern | OpenCode has | syrup adds |
|---|---|---|
| UI | TUI, basic web | Full web app |
| Keys | One key per provider in `auth.json` | Vault with many keys per provider, labels, free/paid flag |
| Routing | Pick one model | Router: best model per chat from your keys, sticky per session, per-model cooldowns, invisible failover before the first token |
| Cost | Per message/session numbers | Ledger, dashboard, budgets, free-vs-paid split, per provider/day |
| Memory | `AGENTS.md`, session history | Long-term memory store exposed as MCP tools |
| Skills | Loads `SKILL.md` | Browse, install, enable from the UI |

## Router

The router (`src/server/router`) is an OpenAI-compatible server registered in OpenCode as the `syrup` provider with two aliases, `syrup/auto` and `syrup/fast`. The same core runs in-process locally and inside the cloud sandbox sidecar (`sidecar/`). The research behind it: gains come from plumbing (feasibility, cooldowns, deadlines, stickiness, measured health), not from an LLM classifier. Switching models mid-session costs quality and kills prompt caching.

- **Candidates.** Every model the engine catalog lists (OpenCode `provider.list`, models.dev data) for a provider the router can reach (one with an OpenAI-compatible base URL in `backends.ts`) and holds a key for: the active vault key, or in local mode the provider's environment variable (except paid-only providers such as Anthropic and OpenAI, so a stray `ANTHROPIC_API_KEY` never spends money through Auto). Anthropic is reached through its OpenAI-compatible endpoint. The catalog lists models an account may not have (Mistral's free plan has no GLM-5.3 or Large), so each key's own `GET /models` list is fetched on first use and hourly (`served.ts`) and unserved models are dropped; an unreadable list, or one matching no catalog id, filters nothing. In the cloud the sidecar holds key metadata only (provider, key id, tier) and refreshes it every minute, right after a rejected key, and when the relay names another key id than the one on record (`x-syrup-key-id`), from `GET /api/ingest/router/keys` (authorised by the sandbox's ingest token), so a key added mid-session applies without a restart. Every relay call names the key id the router has on record (`x-syrup-expect-key`), and the relay reads the database before using any other. OpenCode Zen is never a candidate: its free tier answers 403 "can only be used from within OpenCode" to proxied requests, so Zen models are direct picks only. The Providers page marks other providers the router cannot reach as direct picks too. A key tagged free only yields the models that provider's free tier serves (`buildCandidates`), so a new key defaults to paid unless the curated entry says the provider has a free tier. What syrup knows beyond the catalog lives in `src/lib/model-registry.ts`: a 0–100 coding-agent quality score, speed priors (tokens/s, time to first token), free-tier capacity per model, and which models matter for an agent at all. The model picker reads the same module.
- **Feasibility filter.** Candidates that cannot take the request are dropped before scoring: not usable by an agent (not chat, no tool calling, deprecated, small context), prompt plus output budget larger than the context window or the free tier's tokens-per-minute limit (the output budget is clamped first, so e.g. Groq's 8K TPM still serves tiny requests), image input on a model without vision, one-request-at-a-time providers already busy, or cooling down. A context-length rejection teaches the router a prompt cap for that backend, which expires after an hour. Tool support is read from the catalog's `capabilities.toolcall`.
- **Scoring.** Each remaining candidate gets a score from quality, predicted time (registry priors, replaced by measured time to first token and tokens/s as requests come in; first-token times decay back toward the priors with a 10-minute half-life, so one bad minute does not demote a model for good, while decode speed is learned fast when slower and decays with a 60-minute half-life, since a free endpoint's throughput belongs to the endpoint; OpenRouter `:free` ids start at 25 tok/s and 1.5× first-token time; on Auto the expected output is multiplied by the model's `think` factor for hidden reasoning), error rate, scarcity (a free tier with ~20 requests/day is saved for hard turns) and cost. **Free first:** a paid key wins only when no good free model (quality 70+, or 84+ on a hard turn) can take the turn. A request that is hard only because its session is escalated (below) uses the 70 bar: escalation buys a stronger grade, never money the request's own words would not have bought. On a hard opening, any free model that clears the opening floor also holds paid keys back, so speed alone never buys a paid model. **Auto** favours quality; **Fast** favours predicted time and asks for low thinking effort. A turn is hard when the user asks to plan, debug, design or investigate ("plan A or plan B" doesn't count), or after two tool results in a row that start with an error. On a routine later turn, a candidate predicted slower than max(20 s, 3× the quickest adequate model) loses 30 points (a last resort, never removed); on a hard turn one predicted past 90 s loses 15. A **numeric** turn (arithmetic, a conversion, an estimate, a price comparison; `policy.isNumeric`, Auto only) pays 10 for scarcity instead of 25 and moves to a stronger free model (quality 70+) only when that model is predicted to start within 3 s and finish within 8 s of the current one (reason `numeric`). `SYRUP_NUMERIC_EFFORT=low|medium` (unset: off) asks Gemini Flash-Lite to think on those turns.
- **Stickiness.** OpenCode sends the session id on every model request (`x-session-affinity`, `X-Session-Id`; `x-parent-session-id` for subagents). The router keeps a session on the model it started with, so prompt caches stay warm and behaviour does not drift. It lets go only when needed: the model is unavailable, a hard turn needs a stronger grade (then the best-ranked model of the best grade on offer goes first, whatever outranks it, and stays; paid keys count only where free first lets them win), a scarce free model reaches a new routine user turn, the model became far slower, the session landed there only through a failover (or on a paid key) and the better free backend is back, or a new user turn has a clearly better model on offer. Tool-call continuations stay put.
- **Cooldowns per model, by limit type.** Most failures cool down only that provider/model on that key: Google quotas are per model, and one overloaded model must not bench the rest. Two cases reach wider. A rejected key (401/403) or payment required (402) cools down every model on that key. OpenRouter's daily free-model cap cools down every $0 model on that account. The reason decides how long: per-day limit (until the reset, e.g. midnight Pacific for Google), per-minute limit (the provider's retry delay; Google 429 bodies carry `QuotaFailure` with `PerDay`/`PerMinute` quota ids and `RetryInfo.retryDelay`), overloaded (503), rejected key (401/403, recorded as an auth failure for the provider), timeout, or other error.
- **First-token commit.** The router sends nothing to OpenCode until the chosen backend produces its first token, within a deadline. If the backend errors or misses the deadline first, the router moves to the next candidate and the client never sees the failure. Once a byte is sent, the request is committed to that backend. The deadline for a backend with a fallback behind it is 2× its predicted time to first token, between 8 s and 25 s (measured 2026-10-07 with `pnpm bench:agent`: the old 10–60 s band and 2.5× let a one-word reply wait 16 s on a silent Gemini); the last candidate gets two minutes, and so does a hedge partner with nothing usable behind it (or the first pick, once its partner has failed), so two slow but working backends never both time out where one alone would have answered.
- **The opening turn (2026-10-07; hard openings since Round 1).** A chat's first request (one user message, nothing answered) is where the user stares at a blank screen and nothing is cached, so Auto picks for speed there: among adequate free models, the predicted time to first token weighs four times more than usual (6 points per second, against the whole predicted wall time at 1.5), so the model that answers first wins unless a stronger one is within a couple of seconds of it; models below the floor stay in the list as fallbacks, ranked below. Adequate means quality 60+ on a routine opening, and the registry's strong grade (72+) on a hard one (plan, debug, design, substantial work), or 60+ when no free model is strong. The free models set that floor; when none clears quality 60 (a paid-only key set), all candidates do. Later turns weigh quality again and may move the chat to a stronger model (the usual "released_better" release). The same turn is **hedged**: if the first backend has produced nothing after 0.8× its predicted first-token time (1.5–4 s), the next adequate free, non-scarce backend is started too and whichever produces a token first answers; the loser is cut and recorded as `aborted`/`hedged`, which teaches a first-token lower bound (it can only raise the estimate) and nothing else; the note under the reply does not call a race win a retry ("answered after 2 tries"), and the waiting line does not call the loser dropped. On a hard opening the partner must also clear quality 60, since its answer may be the one the user gets; a partner below the floor the first pick clears (Flash-Lite behind a strong Gemini Flash, the usual Google-only case) starts only once the first pick is actually late, at 1.25× its predicted first token with no 4 s cap, so a strong pick that is on time is never pre-empted and its scarce request never wasted. The partner is never on the first pick's own one-at-a-time key (Z.ai), and it is checked again when the race starts (busy, cooling). One request of free quota, spent only on the opening turn's first streaming attempt, never on scarce models or paid keys. Measured 2026-10-07 before this: the one-word opening turn took 24.8 s on Gemini's bad day (the fallback answered in under 2 s), and the hard "plan" prompt 30–80 s, because quality-first ranking walked through Gemini Flash 503s and timeouts first. **Answer fast, escalate after (decision 13).** A hard opening escalates its session by turns, not by the clock: every request after the quick first answer is hard through the user's next turn, the opening turn's own tool-call steps (their latest user message is still the hard one) and the whole next user turn, even one that reads as routine ("ok, do it") and however long the user took to write it. The user turn after that is judged on its own; the session's 30-minute idle expiry bounds it all. (Repeated tool failures still escalate for 10 minutes.) Stickiness then moves the chat to the best-ranked model of the best grade on offer (`escalated`) and keeps it there; a paid key counts only where free first lets it win, so an escalated "ok, do it" stays on free models when a free one of quality 70+ is on offer. The switch happens at the first request after the first answer: mid-turn when that answer called tools, else at the next user message. Mid-turn, because the hard part of a plan or debug turn is the tool loop after the first reply, and because the switch costs least there: nothing was cached on the opening, so moving costs one cold prefill wherever it happens and the earliest step has the smallest prompt; Gemini validates thought signatures only within the current turn (since the last user text), and for tool calls another model made the router sends the skip value Google documents for traces from another model, as every mid-turn failover already does (Google discourages it because Gemini's own reasoning is lost, but those calls carry none of Gemini's reasoning to lose); models with interleaved reasoning get the empty reasoning field the router already sends after a failover. A chat that opened routine keeps the old rules: a hard later turn ranks quality first from its first step, and nothing after it is escalated.
- **Title calls (decision 16).** OpenCode titles a new chat with one call to its small model (`syrup/fast`) on a fiber of its own; the turn never waits for it. A title is optional, so it gets one backend, 4 s to its first token, no failover and at most 512 output tokens (OpenCode asks for 32K; one title on 2026-10-07 streamed 14,070 tokens for 7 minutes, and a late title overwrites a rename). On Google it asks for `reasoning_effort: "minimal"` (accepted by every Gemini model through the OpenAI-compatible endpoint), since hidden thoughts count against the 512 and delay the first visible token; an answer with no title text that stops at the 512 (`finish_reason: "length"`) is let go like a leash expiry, with no cooldown or error rate, because the cap is the router's own. **A title commits on its title, not on its thinking.** A chat step commits on its first reasoning token, but a title's reasoning (`reasoning_content` on big-pickle, mimo and kimi, `reasoning` on groq's gpt-oss) is buffered and its leash keeps running until the first title text (`policy.hasTitleText`: non-whitespace content once `<think>` blocks are dropped, since OpenCode saves only the answer's text). So a title that thinks until the 512, thinks past its leash, or stalls, dies or stops after thinking gets the router's own title instead of an empty answer, which would have left the timestamp name. A title still thinking at its leash is logged as `no title within 4s, the model was still thinking` and teaches no first-token lesson, because its first token came in time. Once title text arrives, the buffered reasoning and the text stream through untouched. The router knows a title by OpenCode's two fixed texts (the title prompt's first line, then "Generate a title for this conversation:") and no tools, not by size: a title carries the whole first message, and a compaction of a short chat on Fast is small and tool-less too but belongs to the turn. **When the router lets a title go, it writes the title itself (decision 16, option e).** Letting go covers the leash running out, the one attempt failing, an answer with no title text at the 512 cap, every model cooling, no provider connected and the catalog failing to load. In all of these the router answers at once with an ordinary successful completion, in the shape the request asked for: SSE chunks (role and content, a `stop` chunk, a usage chunk with zero tokens, `[DONE]`) or one `chat.completion` JSON. OpenCode's AI SDK parses it as a normal reply and saves it as the title. Its text is made from the chat's first user message (the title request's third message, `policy.fallbackTitle`): the first line that has text once code fences and markdown are stripped, whitespace collapsed, cut at a word boundary to at most 50 characters with `…` when it does not fit. A message that is only code gives the code's first line; one with no text (an image alone) gives `New chat`. It is linear in the message, since it runs on most chats and, in local mode, in the app's own Node process: system reminders are cut in one `indexOf` pass, markup-only lines are skipped by one anchored test, and the markdown regexes (quadratic on markers that never close: a 200 KB line of `**a ` once took about a minute) only see the first 1,000 characters of at most 200 lines, 20,000 characters in all. A 1 MB adversarial line takes under a millisecond. Never an error, because an error leaves OpenCode's default `New session - <ISO timestamp>` for good: OpenCode titles a chat only while it has exactly one real user message and swallows a title error. About 18 of 31 recent chats had a title first token slower than 4 s, so an error would have left most chats with a timestamp for a name. The response carries `x-syrup-title: synthetic`. A title a model answers in time is passed through untouched. A leash expiry or an answer with no title text at the cap is recorded as `aborted`/`title_skipped`, with `synthetic title from the first message (<why>)` in its error column. `aborted` keeps the row out of the success rate, the alias's last pick and the answers list, and `droppedAttempt` already ignores `title_skipped`, so the waiting line never names it. The row teaches only a first-token lower bound: no cooldown, no error rate. A real 429 or 5xx keeps its own failure row and cooldown, and the `request.title_skipped` log line names why and the title it wrote. Title rows carry no session id, so the chat's waiting line and answers never show them, and a title never sets the chat's stickiness. On the 22 titles of 2026-10-07 (Gemini's bad day), 9 had a first token within 4 s; the other 13 took 3–30 s, one 7 minutes, and failover inside 4 s would have saved one.
- **Memory across starts.** A router starts with the registry's guesses and learns from its own requests, which in the cloud means every sandbox start learned Gemini's bad day again on the user's first message. Now `RouterStore.recent()` hands a fresh router the last 15 minutes of this user's attempts (local: SQLite; sandbox: `GET /api/ingest/router/recent`), and `Health.seed()` applies cooldowns still in force and replays first-token times and failures into each backend's stats when it is first seen. The same warm-up fetches every key's served-model list before the first request instead of during it.
- **Learned refusals.** Three failures teach the router something permanent for the process instead of costing an attempt on every request: a 404 "model no longer available" takes that model out for a day with no health penalty; a 400 "thinking level is not supported" (Gemma through Google's OpenAI-compatible endpoint) marks the model as taking no reasoning parameter, and the same backend is retried plain at once without using up an attempt; a 403 that names a model ("only available on …") cools that model for an hour, while only a 401, or a 400/403 whose words blame the key or account, benches every model on the key.
- **Status API.** Every attempt is a row in `router_events` (now with session id, time to first token, retry-at and reason). `GET /api/router/status` derives per-backend health (cooldown and reason, median time to first token, success rate), the model each alias last answered with, and providers whose key was rejected in the last hour. `GET /api/router/answers` lists which model answered each request in a chat. Shapes live in `src/lib/router-status.ts`, so local and cloud read the same thing; the Providers page uses it to flag a rejected key.

**Token efficiency.** `syrupEngineConfig` (`src/server/engine/opencode.ts`, shared by local mode and the sandbox) turns on OpenCode's tool-output pruning (`compaction: { auto: true, prune: true }`; masking old tool outputs costs about half the tokens with equal or better solve rates) and declares the aliases with a 256K context and 32K output. That keeps prompts within reach of the strong free models (mostly 200K–1M windows) and makes OpenCode compact before prompts get slow.

**syrup's OpenCode plugin and the config dirs (2026-10-08, [QUALITY.md](QUALITY.md) Q1).**
- *One plugin, both modes.* `src/server/engine/syrup-plugin.ts` is a single dependency-free file that OpenCode's Bun runs. `sidecar/build.mjs` builds it to `.sidecar/syrup-plugin.js` (`pnpm dev` and `pnpm build` run the build first). `syrupEngineConfig` loads it with `"plugin": ["file://…"]`: locally from `.sidecar/`, in the sandbox from `/vercel/.syrup/syrup-plugin.js`, written in the same `writeFiles` batch as the sidecar. The sidecar's bundle hash covers the plugin, so a reused sandbox restarts onto a new plugin.
- *What it does.* Features are functions of the environment that return hooks or nothing, and they are independent. The eval replay (`SYRUP_EVAL_REPLAY`) makes `websearch` and `webfetch` answer from a cassette with OpenCode's own definitions. Context hygiene (QUALITY.md Q2, on unless `SYRUP_CONTEXT_HYGIENE=0`) works on the web tools only: `numResults` 5 (ceiling 6); search results trimmed to the query (≤ 5 results, ~6,000 characters, cap 8,000, URLs kept, tables whole or cut under their header, rows without a header kept whole under a label); `webfetch` capped at 12,000 characters; web results of earlier user turns sent as a stub with the query and sources (`experimental.chat.messages.transform`: only what is sent changes; storage and the UI keep the text); websearch's definition cut to `{query, numResults}`; OpenCode's post-compaction "continue" request skipped when the compaction followed a finished answer. With both off the plugin returns no hooks. Q4's `webfetch` override joins the same file.
- *Compaction.* Every alias has `limit.input: 120_000`, so auto-compaction fires at ~100K (120K − 20K reserved) instead of 224K.
- *The config dirs are prepared first (Q0's hard rule).* Loading any plugin makes OpenCode install `@opencode-ai/plugin` into every config dir before a workspace's first request: 21.5 s locally, 56 s in a sandbox. `src/server/engine/config-dirs.ts` gives each config dir that has neither `node_modules` nor `package.json` an empty `node_modules/` plus a `package.json` and lock naming the package. A workspace is never written to. The sandbox runs it (`.sidecar/prepare-config-dirs.js`) right before every `opencode serve` (`/vercel/.config/opencode`, `/vercel/.opencode`: syrup's own dirs). Locally only the eval engine (`SYRUP_EVAL=1`, its own XDG dirs) prepares; the user's real `~/.config/opencode` is never seeded, because an empty seed looks installed and a tool or plugin the user adds there later could then not find `@opencode-ai/plugin` (found in the Q1 review). Instead `warmEngine` boots the Home workspace and the launch folder right after spawn, so OpenCode's one real install (~21 s, once per machine) runs in the background before anyone types. Measured locally: first request 0.31 s with the plugin against 0.51 s without; 11–20 s with the plugin and nothing prepared.
- *Eval traffic.* An eval engine (`SYRUP_EVAL=1`, `pnpm eval`) sends `x-syrup-eval: 1` on every model request; the router's `rank()` then drops scarce free backends entirely ([TESTING.md](TESTING.md) §1.2).

## Phasing

**Phase 1 — drive OpenCode from the browser.** ✅ Spawn `opencode serve`, relay SSE, render sessions and streaming messages, handle permissions and questions. Ledger reads cost/tokens from OpenCode messages.

**Phase 2 — key vault + router.** ✅ Vault: many encrypted keys per provider with a free/paid tier; the active one is written into OpenCode auth. Router: an in-process OpenAI-compatible server (port 4210) registered in OpenCode as the `syrup` provider with `syrup/auto` and `syrup/fast`. It resolves an alias to ranked backends from the user's connected keys (free tiers first), injects the key, fails over on 429/5xx with per-key cooldowns, and logs every attempt with real cost to `router_events`. OpenCode Zen free models cannot be routed (they only accept requests from OpenCode itself); they remain selectable directly. Since superseded by the routing described under [Router](#router): per-model cooldowns, session stickiness and first-token failover.

**Phase 3 — memory + skills.** ✅ Memory: `memories` table with an FTS5 index (no embedding model needed), a Streamable HTTP MCP server on the router port exposing `memory_search/list/get/save/update/forget`, and a generated `data/memory/MEMORY.md` loaded as engine instructions so the agent always sees its index. Skills: list from the engine, create from pasted `SKILL.md`, install from GitHub (packs supported) into `~/.config/opencode/skills`, remove.

**Phase 4 — product completeness.** ✅ Workspaces (per-folder sessions, native OS folder dialog, typed paths, recents), session rename/delete, attachments (images/files as data URLs), Changes panel (engine snapshot diff, falling back to files touched by write/edit tools), first-run banner, production build verified.

**Logs.** ✅ `slog()` writes structured events (level, source, event, session, directory, redacted JSON) to the `logs` table in batches, so hot paths never wait on SQLite. A Logs modal, opened from the sidebar, shows them app-wide by default and copies a debugging bundle.

**Folder dialog.** The server opens the OS dialog on its own desktop (self-hosted, so browser and server share one). Windows: the modern Explorer picker (`IFileOpenDialog`, folder mode) called over COM from Windows PowerShell 5.1, owned by an invisible TopMost window so it opens in front. macOS: `osascript choose folder`. Linux: `zenity`, then `kdialog`. One dialog at a time; a new request replaces a stuck one; 3-minute timeout.

**`.sarib` (optional).** `src/server/sarib.ts`. The `sarib` MCP server is added per workspace, and only to folders with a `.sarib` file within three levels (dependency and build folders skipped; rescanned at most once a minute). The OpenCode proxy triggers the check on any request with a `directory`, and waits for it (up to 5 s) before a prompt so that turn already has the tools. OpenCode keeps MCP state per directory and runs local servers there, so the server sees only that workspace. Other workspaces never pay for its tool definitions. Needs Python 3.10+ and `sarib[mcp]`; the Skills page has an **Enable** button that runs `pip install --user "sarib[mcp]"` in the background (`/api/sarib`).

**Two modes (2026-09-24).** `SYRUP_MODE=local|cloud` (auto: cloud on Vercel) in `src/server/env.ts`. Everything above is local mode. Cloud mode is the hosted product at syrup.syedsarib.com, designed in [PLAN.md](PLAN.md): Google sign-in (Auth.js v5, JWT sessions, open to any verified Google account), Neon Postgres with forced row-level security (`src/server/db/pg`, every tenant query inside `withUser()`), per-user envelope-encrypted provider keys (`src/server/cloud`), legal documents with recorded consent, PostHog analytics with opt-out, admin page. The agent itself (a Vercel Sandbox per workspace) is Phase 2; until then cloud mode blocks the local-engine routes with 501 in `src/proxy.ts`.

**Local hardening (Phase 0, 2026-09-24).** Server binds 127.0.0.1; `src/proxy.ts` rejects non-loopback Host and cross-origin mutations; the OpenCode server runs with a per-process password that only the `/api/oc` proxy and server modules know; router and memory MCP require the same secret as bearer; the vault key lives in the user config dir, outside any workspace.

**Cloud runtime (Phase 2, 2026-09-24).** One Vercel Sandbox per workspace (`src/server/engine/sandbox.ts`): universal image, fra1, 1 vCPU, 10-minute idle timeout extended by a heartbeat while the tab is visible, last snapshot kept 7 days. On create: OpenCode 1.18.32 pinned + repo clone (private GitHub via a one-shot credential helper reading process env). On every start: the esbuild-bundled **sidecar** (`sidecar/`, the same router core and memory tools as local mode) is uploaded and started with the user's key metadata (provider, key id and tier, never a secret), an ingest token and a per-start secret in process env; OpenCode is started with a per-start password and a config pointing its `syrup` provider and memory MCP at the sidecar on loopback. Only OpenCode's port is public; the browser connects to it directly with Basic auth held in memory (`src/lib/oc.ts`, `EngineProvider` connection). The sidecar taps OpenCode's event bus and posts sessions, messages, router attempts, memory ops and logs to `/api/ingest/*` with a 60-minute HMAC token bound to user, workspace and engine start; Postgres is the history, the sandbox is disposable. Provider calls leave the sandbox only through the app's **LLM relay** (`/api/ingest/llm/<provider>/chat/completions|models`, `src/app/api/ingest/llm/`): the router's base URL for every provider points there and its bearer is the ingest token; the relay adds the user's real key and streams the provider's answer back unbuffered (see *Secrets, cloud* below). Egress: private networks and the metadata service always denied; a workspace with listed hosts runs a strict allow-list, which no longer needs provider hosts. Kill switch `SYRUP_AGENT_ENABLED=0`. Measured: cold 9–15 s, warm resume 7 s, hot 0.3 s, ~7–25 CPU-seconds per boot-and-prompt.

**Home workspace (2026-09-28).** Every user has a workspace named Home that needs no setup, is listed first with color 0, cannot be removed, counts toward the cap of 8, and is where new chats start. Local: the folder `~/syrup` (`%USERPROFILE%\syrup`), created by `GET /api/workspace/home`; a first visit (no saved folder) opens it, and an existing full list makes room by dropping its least recently used folder (chats stay on disk). Cloud: a `workspaces` row with `is_home` (migration 0009), created by `ensureHome()` on the first list or visit to `/`; the partial unique index `workspaces_home_idx` plus `insert … on conflict do nothing` keeps it to one per user under concurrent requests, and `DELETE /api/workspaces/:id` refuses it. `/` redirects to Home. Opening a sandbox never blocks the UI: the app prewarms Home's sandbox on load, `src/lib/home.ts` shares the in-flight open with the workspace view, the `/w/[id]` layout keeps one connection across the new-chat screen and chats, and `createSession`/`send` in `EngineProvider` wait for the engine, so a message typed early shows as pending and goes out when it connects.

**Warm-up (2026-10-07).** What runs before the first message can be answered, and what the user sees meanwhile.
- *What warms when.* Cloud: Home's sandbox starts when the app loads (`prewarmSandbox`), and so does the sandbox of the workspace with the most recent chat of the last 24 hours; another workspace starts when opened. After a sandbox start, `openWorkspace` asks OpenCode for the folder's session list, which builds the per-folder instance (~3 s) before the browser needs it. Inside the sandbox, the sidecar's router fetches served-model lists and seeds its health memory at start. Local: the engine, router and memory start with the app; the per-folder instance builds on the first request for a folder (the page load's session list); the router warms the same way.
- *What the user sees.* `src/components/warm-up.tsx`, on the new-chat screen only. After 1.2 s of waiting: the stage by name ("Starting your workspace" → "Starting the engine"), the usual length of this wait from this browser's last five waits, "taking longer than usual" past 1.5× that, and whether a typed message is queued. The composer stays usable throughout. Mid-turn, `router-progress.tsx` says which model was dropped and why ("Gemini 3.8 Flash is overloaded. Trying another model…"), polling `/api/router/answers?live=1` every 2 s only while a first token is awaited.
- *The game.* Reviewed by a three-voice adversarial council (for, against, judge) with the research on waiting: occupied time feels shorter and explained waits feel shorter, but a game needs ~3 s to pick up, hides progress if it is a modal, and fights the composer on phones. Verdict: ship inline, not as a modal. A one-button canvas game (a spoon hops over syrup spills) appears under the status line after 3 s of waiting, on a mouse/trackpad only, never on phones, never over the composer, closes with the wait, and a single dismissal keeps it away for good (`syrup.warmup.game`). PostHog: `warmup_ready`, `warmup_played`, `warmup_dismissed`.

**Streaming, reconnect and secrets (2026-10-08, Round 1b).**
- *Streaming text.* OpenCode 1.18 sends a text or reasoning part as an empty `message.part.updated`, then `message.part.delta` events (`{ sessionID, messageID, partID, field, delta }`), then a final `message.part.updated` with the whole text. The engine stores a streaming part empty and its event stream replays nothing. The store (`src/lib/engine-store.tsx`) applies deltas only to parts this page watched from their empty start (`live`), joined per part and flushed at most once per animation frame (a 100 ms timer covers hidden tabs); a part's own update is authoritative. A part joined mid-stream shows "Writing…" until its final update. A stream drop turns live parts "frozen": their text stays, with "Writing…" under it, and deltas are ignored until the final update.
- *Stale reads.* Every stream event gets a sequence number; a messages read carries the number from when it was sent, and the merge keeps whatever the stream touched later, keeps open parts and messages that started after the read, and never brings back what the stream removed. A read older than the chat's last applied read is ignored.
- *Rendering.* Finished text is plain Markdown. Text watched as it streamed renders through `LiveText` (`src/lib/use-typewriter.ts`, a lazy chunk preloaded when a chat opens): what is there at mount shows at once, growth trails the stream by about 0.25 s, finished top-level blocks render once and only the growing tail is re-parsed (`settledBlocks`, guarded by `scripts/fixtures/settled-blocks-check.mjs`). `MessageView` is memoized. The chat follows while busy, for 1 s after the turn, and while text is still revealing; only the reader scrolling up lets go.
- *Reconnect.* On every connect the store reads `GET /session/status`, `/permission` and `/question` (scoped by directory) and merges them, events during the reads winning: after a reload a busy chat shows Stop and its permission or question card comes back.
- *Secrets, local mode.* The `/api/oc` proxy accepts only allow-listed engine routes (compared case-folded; anything else 404, a malformed segment 400), refuses any request whose directory or file path reaches OpenCode's data, config or state folder or syrup's config folder (403), and scrubs secret fields from the JSON of `config/providers`, `provider`, `config`, `global/config` and `agent`: provider keys, secret-named options (the internal secret is the engine password, the router secret and the memory MCP bearer at once), header and MCP environment maps, credentials in URLs. The event stream is never buffered. A new UI feature that calls another engine route must add it to the allow-list.
- *Secrets, cloud: the LLM relay (2026-10-08).* No provider key ever enters a sandbox. What the sandbox holds: key metadata (provider, key id, tier) from `SYRUP_ROUTER_KEYS`, the ingest token (60 minutes, bound to user, workspace and the engine start), the per-start router secret and OpenCode's password. What was removed: the `SYRUP_KEYS` env with the decrypted keys, `GET /api/ingest/keys` that returned them, the plaintext exporters in `keys.ts`, and provider hosts in the egress allow-list. Per call the relay (`relay.ts`): checks the token first; refuses a token whose sandbox session is not the workspace's current, live one (`sandboxes.status` and `last_session_started_at`), so stopping, deleting or restarting a workspace ends its old token within the cache's fresh window plus one call; allows only the two paths per known provider, never a query string or a redirect; reads the user's keys and sessions from a per-instance cache (fresh 10 s, then served at once while one background read refreshes it, for up to an hour; a failed refresh is ridden out for a minute, then calls fail as the app's own error; every read gives up after 4 s and never waits for migrations); re-reads the database before using a key other than the one the sidecar expects, or one the provider just rejected (that provider only); applies the spend policy (`policy.ts`); calls the provider's fixed URL with an allow-list of headers; streams back only the headers the router learns from, plus `x-syrup-key-id`. Spend policy, on every chat call whoever holds the token: a key tagged free may call only what the router's free-key rule allows (on Google, Mistral, NVIDIA, Groq, Cerebras and Cohere the models with a free quota; elsewhere $0 models, so a free OpenRouter key never reaches the account's credits); a paid key only a model the app's own models.dev catalog lists for that provider and the router could pick, with `max_tokens` and `max_completion_tokens` capped at the model's output limit; `n` above 1 is refused. Every paid-key call is logged twice (`relay.paid_call` with user, provider, model and output cap; `relay.paid_usage` with the tokens the answer reported), in the logs table and as a runtime log line. Every answer the provider did not write carries `x-syrup-relay-error`, and the router classifies those apart from provider failures (`upstream-errors.ts`): a database blip, a dead token or a platform error cools nothing and marks no backend unhealthy (reason `relay`; the sidecar retries a database blip once after 300 ms); a refused model benches only that backend for an hour; an unreachable provider counts as a network error, as direct. The relay route is the one `/api` path `src/proxy.ts` does not run on (no second invocation per model call, no 4 MB middleware body cap); it is fail-closed on its own (404 in local mode, the token before anything else). `vercel.json` turns on `supportsCancellation` for it alone, so a sidecar that goes away (a hedge loser, a first-token timeout, the title leash, Stop) aborts `req.signal` and with it the provider call; Next 16.3's own route pipeline propagates the disconnect (`scripts/test-llm-proxy.mjs` scenario 16). A body over a Function's 4.5 MB request limit is fitted in the sidecar (`relay-fetch.ts`): the oldest inline images give way to a one-line note, this turn's images never; text that cannot fit answers as a context overflow (`context_length_exceeded`), so OpenCode compacts, and no prompt cap is learned from an image count. A reused sandbox whose sidecar is not this deploy's (bundle hash on its `/health`) is restarted when opened. An answer still streaming at 290 s is closed cleanly and recorded as truncated (Hobby's 300 s ceiling includes streaming).
- *Still reachable, known.* Local: a script in the page's own origin can still drive the agent, by design. Cloud: the browser talks to the sandbox's OpenCode directly, so none of the proxy checks apply there. The ingest token is readable inside the sandbox (`/proc/<pid>/environ`) and default egress is open, so a prompt-injected agent can use it, from anywhere, until its session ends (at most 60 minutes): through the relay it can call the user's providers for exactly the models the router could pick (free quota on free keys; on a paid key, any agent-usable catalog model, output capped at the model's limit, every call logged but not budgeted), and it can write through the other ingest ops; it can never read a key. A key's tier is what the user declared: a key tagged free on a provider whose free tier covers listed prices is billed if that account has billing on. A key removed in Settings is caught on other instances through the sidecar's expected key id (its metadata is at most a minute old); while the database is failing, a cached key is used for at most a minute. A model newer in the sandbox's catalog than the app's copy (refreshed every 6 hours) is refused for paid keys until the app's copy catches up. A tool call needing more than about 290 s of generation is cut at the relay's deadline and may be regenerated and cut again. Keys that were active while a sandbox ran before this change were readable inside it and should be rotated at the provider.
- *Side pane.* On desktop the chat keeps at least 440 px at every window size; the saved pane width is kept for larger screens.

## Known issues

- ✅ Router verified with a real Google key (2026-09-23): a tool-calling turn hit a 503 on `gemini-3.8-flash`, failed over to `gemini-3.5-flash-lite`, and the follow-up turn (which needs the Gemini thought signature restored) succeeded on `gemini-3.8-flash`.
- Gemini 3.8 Flash on the free tier returns 503 "high demand" and 429 often. Observed before the router rewrite: one 503 put the whole Google key into cooldown, Gemini 3.5 Flash-Lite averaged 49 s to first byte, and one failed attempt hung 31 s with no deadline. Per-model cooldowns and the first-token deadline address these.
- ✅ Fixed 2026-10-07: a workspace folder that was moved or deleted. The engine accepted the session and failed the first prompt with a bare "Unexpected server error". The local proxy (`/api/oc`) now answers 404 with a plain sentence for any request naming a missing `directory`; the workspace list probes its folders on load (`/api/workspace?probe=1`), marks a missing one "Folder not found" in the switcher and moves the app to Home if it was the open one; a refused prompt or session create now shows its message in the chat instead of nothing.
- ✅ Fixed 2026-10-07: the Changes panel was always empty. Two causes. (1) OpenCode 1.18 keeps diffs per user message (`info.summary.diffs`, a full-context unified `patch` per file, written after the turn settles); `GET /session/{id}/diff` answers `[]` without a user `messageID`, and syrup asked without one. The panel now reads the summaries already in the message store (no request at all) and merges turns per file (`src/lib/diffs.ts`, tested by `scripts/test-diffs.mjs`): first-before against last-after, so a line edited three times counts once. (2) The engine snapshots only git worktrees, so Home (`~/syrup`) and empty cloud workspaces never had diffs or revert. Home gets `git init` (no commits) when created or first visited; cloud empty workspaces get it at create, and existing sandboxes catch up on their next start. Other non-git folders say so in the panel.
- ✅ Fixed 2026-10-07: duplicate skill names. The engine lists one copy per name and may switch after a reload, so a skill seemed to vanish. `listSkills` now scans every root the engine reads (`~/.config/opencode/skills`, `~/.claude/skills`, `~/.agents/skills`, and `.opencode|.claude|.agents/skills` in the workspace) and reports the other copies per skill; the Skills page shows a notice and the paths. The engine still decides which copy loads; the user keeps one.
- OpenCode Zen free models cannot be routed by syrup: the free tier answers 403 "can only be used from within OpenCode" to proxied requests (observed live). They remain selectable directly in the model picker; Auto and Fast never use them.

## Data (SQLite via Drizzle)

- `provider_keys` — provider id, label, encrypted key, tier (free/paid), rate-limit hints, enabled.
- `usage_events` — one row per assistant message: session, message, provider, model, tokens, cost, timestamp, key used.
- `router_events` — one row per routed request: alias, provider, model, key, tier, status, attempts, latency, time to first token, tokens, real cost, error, session id, retry-at and reason. Source for the router status API.
- `memories` — id, kind, content, embedding, tags, source session, timestamps.
- `logs` — structured application log: timestamp, level, source, event, session, directory, redacted JSON data.
- `settings` — key/value.

OpenCode keeps its own session and message storage. syrup does not duplicate it; the ledger keys off OpenCode message ids.
